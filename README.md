# Glissform website

The website is a Vite, React, TypeScript, and SCSS project. Its desktop page follows the [Figma design](https://www.figma.com/design/IkSrf5xF80j0PeRMzPytZ8/Untitled?node-id=56-2717) and adds fixed Customisable, Private, and F.A.Q navigation. As soon as scrolling begins, the same navbar smoothly gains a translucent, blurred material and removes it again at the top. The selected link follows the linked section occupying the largest visible area; the brand returns to the top and clears the selection. The 320–768px version presents the same product content in a fluid single-column layout; the full desktop layout starts at 1156px. The 769–1155px version adapts the same content into a compact layout with two-column grids. Responsive layouts and optimized images are included in the website deployment; `/deployment.json` identifies the currently published commit. The clickable feature cards switch between still previews every ten seconds, with a slim progress bar, smooth automatic and manual preview transitions, and matching hover, pressed, and keyboard-focus feedback. The Customisable grid has interactive blur choices, a starting-angle slider, and switches; timing values are illustrations.

One fluid layout covers this range with no intermediate width breakpoint. The single-row header pairs the brand with a 44px burger button. Its content-width dropdown sits 8px below the button with their right edges aligned and contains Customisable, Private and F.A.Q links; the navbar download button is hidden on mobile. The menu closes after navigation, on Escape, on outside interaction and when resizing above 768px. Escape returns focus to the button. Anchor offsets and active-section tracking account for the compact header. The same main content, headings, image descriptions, FAQ, requirements, privacy facts and download URLs serve mobile and desktop on the same URL; mobile content does not require opening a menu or changing a preview to be available. Responsive line breaks let the existing wording wrap naturally on small screens. Typography, gutters and spacing scale within the range, while the blue glass buttons, neutral surfaces, rounded cards and final dark download panel retain the desktop visual language.

Feature choices and their preview stack vertically, with the same selected and dimmed unselected states as desktop. Settings, everyday controls, Privacy and FAQ use one column. Navigation links, sliders and switches have at least 44px-high interaction areas. The MacBook scroll demo scales to width and viewport height, with a shorter mobile scroll distance and the existing reversal and reduced-motion/graphics fallbacks. The future-features dot field uses its still SVG with an undistorted centered crop on mobile. The original responsive layout was checked in the local browser. The burger-menu change passes the production build and source checks. Its opening, Escape dismissal/focus return and right-edge alignment with an 8px button gap are verified in the 390px local browser preview. Physical mobile Safari/Chrome rendering is not verified. Google homepage indexing was verified in Search Console on 2026-10-02, as recorded in the loading/indexing audit. Production builds include the full page content in the initial HTML; the browser hydrates that same markup to attach interactions.

No server-side JavaScript runtime is required in production. `hydrateRoot` attaches the existing browser interactions to the rendered page; development keeps the usual client-rendered workflow. Direct section links restore their initial position as fonts and the animated track settle, then stop tracking on visitor input, navigation or resize. Headlines use CSS-controlled breaks with real spaces, so mobile wrapping and readable text are present before JavaScript runs. Product descriptions, feature cards, requirements, privacy facts, FAQ, image descriptions and download links are in the initial HTML. The interactive MacBook demo requires JavaScript and is hidden when scripting is disabled; its surrounding product text and sleep note remain available.

## Loading efficiency

Live loading was measured with three Google PageSpeed Insights runs on 2026-10-02 against deployed commit `e88c9ea`. Median performance scores were 65 on simulated mobile and 83 on desktop; all runs scored 100 for Lighthouse SEO checks. Mobile LCP ranged from 1.4 to 7.2 seconds, and desktop from 0.8 to 1.3 seconds. Remaining findings include intermittent font-associated mobile layout shifts, oversized image delivery and startup JavaScript blocking. No real-user Core Web Vitals data was available. See [the audit](docs/live-loading-audit-2026-10-02.md) for every sample, public report links and Search Console status. These loading measurements do not benchmark animation smoothness or prove indexing.

Original PNG artwork lives in `artwork/`. Before development or a production build, Sharp generates lossless WebP screenshots and textures at their original resolution, plus 64/128/256px brand icons and a 64px PNG favicon. Generated files are excluded from Git; Vite fingerprints imported assets for safe caching. Content, layout, colors and animation timing remain unchanged. The first feature preview has high download priority; the alternate preview has low priority so it is ready for the existing automatic/manual transitions. Lower-page preview images load lazily with explicit dimensions.

The build also writes gzip sidecars for JavaScript, CSS and SVG assets. `npm run preview` serves those to gzip-capable clients and applies the intended cache policy: one year for fingerprinted assets, revalidation for HTML and unfingerprinted files. The matching `config/website-performance.nginx.conf` was installed on 2026-10-02 as `/etc/nginx/snippets/glissform-website-performance.conf` and included in the existing HTTPS server block. The server configuration passed `nginx -t` and a graceful reload. Production serves gzip HTML, JavaScript, CSS and SVG, with an uncompressed fallback when requested. Fingerprinted scripts, styles, fonts and images use one-year immutable caching; HTML, the social image, unfingerprinted assets, robots, sitemap and deployment marker revalidate. Live checks verified identical decoded content, `Vary: Accept-Encoding`, gzip refusal, conditional 304 responses, and the existing download/update-feed policies, including partial DMG downloads. The main JavaScript transferred 139,005 bytes instead of 415,205; CSS transferred 9,047 instead of 42,308. Server backups are under `/root/glissform-performance-backups/`. Website deployment uploads assets and does not install or replace this server configuration.

The public server serves `/var/www/glissform.app`. Publish `dist/assets/` before replacing `index.html`, so the new page never refers to files that are not yet available. Preserve the existing `downloads/` and `updates/` directories: they contain the public DMG and signed app update feed. Update the public beta version in `src/siteMetadata.ts` only when a new public version and its DMG are available; page buttons and app metadata share the corresponding download URL.

## Source and automatic deployment

The canonical source is the private repository `itsgeorge22/glissform-website`. Develop in `/Users/george/Projects/glissform-website`. Pushes to `main` and manual runs of **Deploy website** build committed source with Node 22 and publish to glissform.app. Check the Actions run before calling deployment complete.

`WEBSITE_DEPLOY_SSH_KEY` is a repository Actions secret for a dedicated website account. The server accepts only `deploy <commit SHA>` through `scripts/receive-deploy.py`; shell commands and SSH forwarding are disabled. The pinned public host key is in `config/production-known-hosts`. Credentials, generated builds and dependencies are excluded from Git.

The receiver accepts only `index.html`, `robots.txt`, `sitemap.xml` and `assets/`, publishes assets and discovery files first and atomically replaces the page. Legacy builds without the discovery files remain supported. It retains older assets and preserves `downloads/` and `updates/`. `/deployment.json` identifies the published commit. Native app source and release deployment remain separate.
